# 缺陷记录

记录本项目发现过的 4 个问题。**每个缺陷都按同一套模板写**：能复现、能定位、能回归——
这比"修好了"三个字有说服力，也是测试岗面试最容易被追问的地方。

---

## 0. 缺陷管理约定

**严重级别（对业务的影响）**

| 级别 | 含义 | 例子 |
|---|---|---|
| S1 阻断 | 核心功能不可用、数据丢失 | 服务起不来、创建接口 500 |
| S2 严重 | 主流程能走但结果错、脏数据入库 | 非法日期被接受、金额算错 |
| S3 一般 | 边界场景不对、体验受损 | 空名字能创建、负数价格 |
| S4 轻微 | 极端场景、潜在风险 | 并发下的极小概率竞态 |

**优先级（修的顺序）**：P0 立即修 / P1 本迭代内 / P2 排期 / P3 有空再说。

> 严重级别看**影响**，优先级看**紧急程度**，两者不总是一致：
> BUG-003 影响小（S4），但修复只要两行，所以优先级给到 P2 顺手改掉。

## BUG-001 姓名留空也能创建预订

| 项 | 内容 |
|---|---|
| 编号 | BUG-001 |
| 模块 | `POST /booking` 创建预订 |
| 发现方式 | 数据驱动用例（`data/booking_cases.json` → "名称为空"） |
| 严重 / 优先级 | S3 一般 / P1 |
| 状态 | 已修复，已回归，已关闭 |

**环境 / 前置**：本地 mock 服务；已拿到 token。

**复现步骤**

1. `POST /auth` 用 `admin/password123` 换 token；
2. 带 token 发 `POST /booking`，body 里 `firstname` 为空串：

```json
{"firstname": "", "lastname": "刘", "totalprice": 100, "depositpaid": true,
 "bookingdates": {"checkin": "2026-11-10", "checkout": "2026-11-12"}}
```

**期望**：400，提示名字不能为空。
**实际**：200，预订被创建，库存里多了一条没有姓名的记录。

**根因**：`validate()` 只检查了"字段是否存在"和"类型对不对"，没有检查字符串内容是否为空。

**修复**：在 `mock_server.validate()` 里加：

```python
for field in ("firstname", "lastname"):
    if not str(body.get(field, "")).strip():
        return f"{field} 不能为空"
```

**回归验证**：`python -m pytest tests/test_data_driven.py tests/test_validation.py -q` →
原先失败的 2 条用例变绿，全量 64 passed。

**经验**：字段"存在" ≠ 字段"有效"。等价类里一定要有"空串 / 纯空格"这一档。

## BUG-002 不存在的日期 2026-13-45 被接受

| 项 | 内容 |
|---|---|
| 编号 | BUG-002 |
| 模块 | `POST /booking` 日期校验 |
| 发现方式 | 数据驱动用例（"日期不合法"） |
| 严重 / 优先级 | S2 严重 / P0 |
| 状态 | 已修复，已回归，已关闭 |

**复现步骤**

1. 带 token 创建预订，`bookingdates.checkin` 填 `2026-13-45`；
2. 观察响应。

**期望**：400，提示日期不合法。
**实际**：200，创建成功——13 月、45 日都被当成合法日期。

**根因**：日期校验只用了正则 `^\d{4}-\d{2}-\d{2}$`，它只能保证"位数对"，管不了"日期是否真实存在"。

**修复**：改用 `datetime.strptime` 真解析，并补上"退房必须晚于入住"的业务规则：

```python
try:
    checkin = datetime.strptime(str(dates["checkin"]), "%Y-%m-%d")
    checkout = datetime.strptime(str(dates["checkout"]), "%Y-%m-%d")
except ValueError:
    return "bookingdates 里的日期不是合法日期"
if checkout <= checkin:
    return "退房日期必须晚于入住日期"
```

**回归验证**：数据驱动 7 条全绿；另补了闰日边界（`2028-02-29` 通过、`2026-02-29` 拒绝）。

**经验**：**格式校验 ≠ 语义校验**。正则管形状，`strptime` / 业务规则管真假。

## BUG-003 并发删除可能返回两个 201（潜在竞态）

| 项 | 内容 |
|---|---|
| 编号 | BUG-003 |
| 模块 | `DELETE /booking/{id}` |
| 发现方式 | 写并发用例时做代码审查（**实测未复现**：30 轮 × 8 线程并发删同一条，240 次删除全部只有一个 201） |
| 严重 / 优先级 | S4 轻微 / P2 |
| 状态 | 已修复（防御性），已回归，已关闭 |

**代码病灶**（修复前的写法）：

```python
if key not in STORE.all():          # ① 先查：还在
    return self._send(404, ...)
with STORE.lock:
    STORE.items.pop(key, None)      # ② 再删：这中间别的线程可能已经删了
return self._send(201, "Created")
```

**问题**：① 和 ② 之间不是原子的。两个线程同时通过 ①，然后都执行 ②（`pop` 对不存在的 key 不会报错），
于是**两个请求都返回 201**，都以为自己删成功了。

**复现尝试**：10 线程 / 8 线程压测多轮都没撞上——这个窗口只有几微秒，GIL 下概率极低。
但这属于"结构上就错"，不因为难复现就不修。

**修复**：把"检查 + 删除"合并进同一把锁（`Store.delete()`）：

```python
def delete(self, key):
    with self.lock:
        return self.items.pop(key, None) is not None
```

**回归验证**：`test_concurrent_delete_only_one_wins` 连续跑 10 次稳定通过（恰好 1 个 201 + 4 个 404）。

**经验**：并发缺陷有两类——"能稳定复现的"和"靠审代码才能发现的"。后者写进用例是为了**防回归**，
不是为了"证明现在有 bug"。

## BUG-004 负数价格也能创建预订

| 项 | 内容 |
|---|---|
| 编号 | BUG-004 |
| 模块 | 创建 / 更新预订的金额校验 |
| 发现方式 | 补"等价类划分"时发现漏了"无效类：负数"，先写用例再修代码 |
| 严重 / 优先级 | S3 一般 / P1 |
| 状态 | 已修复，已回归，已关闭 |

**复现步骤**：带 token `POST /booking`，`totalprice` 填 `-1`。

**期望**：400，提示价格不能为负。
**实际**：200，创建成功（`totalprice: -1` 入库）。

**根因**：`validate()` 只判断了 `isinstance(totalprice, (int, float))`，没判断取值范围。

**修复**：

```python
if not isinstance(body.get("totalprice"), (int, float)):
    return "totalprice 必须是数字"
if body["totalprice"] < 0:
    return "totalprice 不能是负数"
```

**回归验证**：新增 `test_negative_price_is_rejected`（修复前红、修复后绿），
`pytest tests/test_validation.py` 18 passed。

**经验**：这次的顺序是**先设计后写码**——等价类表格逼着你把"负数"这一格填上，
用例先红、代码后绿，这就是测试驱动的一个缩影。

## BUG-005 只读账号能改数据、能删数据

| 项 | 内容 |
|---|---|
| 编号 | BUG-005 |
| 模块 | `POST /auth` 引入了角色（admin / viewer），但写接口的权限校验只加在了"创建"上 |
| 发现方式 | 新增 `tests/test_roles.py`：用 viewer 账号登录后去改、去删 |
| 严重 / 优先级 | S2 严重 / P0 |
| 状态 | 已修复，已回归，已关闭 |

**环境 / 前置**：`viewer / viewer123` 登录拿 token。

**复现步骤**

1. `POST /auth` 用 `viewer` 登录 → 拿到 `viewer-token-456`；
2. 用这个 token 发 `DELETE /booking/1`；
3. 观察响应与数据。

**期望**：403 `{"error": "需要 admin 权限"}`，数据仍在。
**实际**：201 `"Created"`——数据被删了。

**根因**：加角色的时候只改了 `do_POST`，`do_PUT` / `do_PATCH` / `do_DELETE` 仍然只判"有没有 token"，没判"是不是 admin"。
**这类问题比"没做权限"更常见**：做了一半，检查了一个入口，漏了另外三个。

**修复**：抽一个 `_admin_only()`，四个写接口统一调用：

```python
def _admin_only(self):
    role = self._role()
    if role is None:
        self._send(403, {"error": "forbidden"})
        return True
    if role != "admin":
        self._send(403, {"error": "需要 admin 权限"})
        return True
    return False
```

**回归验证**：`pytest tests/test_roles.py -v` 6 passed（含"删完数据要还在"的二次断言）。

**经验**：权限用例要按"动词"铺全，不能只测一个写接口；**改权限模型时，先把所有写接口列出来再逐个打勾**。

## BUG-006 10 人抢 5 间房，卖出了 9 间（超卖）

| 项 | 内容 |
|---|---|
| 编号 | BUG-006 |
| 模块 | 房间库存 `POST /booking?roomtype=limited` |
| 发现方式 | `tests/test_inventory.py::test_concurrent_booking_does_not_oversell` |
| 严重 / 优先级 | S1 阻断 / P0 |
| 状态 | 已修复，已回归，已关闭 |

**复现步骤**

1. `limited` 房型初始 5 间（`GET /rooms` 可查）；
2. 10 个线程同时 `POST /booking?roomtype=limited`；
3. 统计响应码和最终库存。

**期望**：5 个 200 + 5 个 409，库存归零。
**实际**：**9 个 200**，库存变成 -4——卖出去了 9 间。

**根因**："先查库存、再扣库存"两步之间没有锁：

```python
if STORE.stock_of(roomtype) <= 0:      # ① 查：还有 5 间
    return 409
key = STORE.create(body, roomtype)     # ② 中间被人插队
STORE.take_one(roomtype)               # ③ 扣：这时候可能已经 -1 了
```

10 个请求同时通过 ①，于是 10 个都执行了 ③。

**为什么这条能稳定复现**：mock 里用 `time.sleep(0.01)` 模拟"查库存要访问数据库"的真实耗时，
这 10ms 就是竞态窗口。真实系统里这个窗口通常更大（一次 SQL 查询 + 网络往返）。

**修复**：把"查 + 扣"合并进同一把锁，并删掉模拟延迟：

```python
def reserve(self, roomtype):
    with self.lock:
        left = self.stock.get(roomtype, 0)
        if left <= 0:
            return False
        self.stock[roomtype] = left - 1
        return True
```

**回归验证**：`test_concurrent_booking_does_not_oversell` 从"9 个 200"变成"正好 5 个 200 + 5 个 409"，
且 `GET /rooms` 库存为 0；连续跑 10 次稳定通过。

**经验**：并发缺陷的典型形状是**"检查"和"动作"分开**。凡是"先判断再修改"的代码，都要问一句：
这两步之间，别人能插进来吗？

## BUG-007 异常回调引用了 except 块外已失效的变量

| 项 | 内容 |
|---|---|
| 编号 | BUG-007 |
| 模块 | `tester_gui.py` 扫描线程的异常处理 |
| 发现方式 | ruff 静态检查（F821 未定义名字） |
| 严重 / 优先级 | S3 一般 / P1 |
| 状态 | 已修复 |

**复现步骤**：在体检器里选一个不存在的目录（或让扫描过程抛异常），触发 `_scan_worker` 的 `except` 分支。

**期望**：界面提示"扫描失败：xxx"。
**实际**：回调执行时抛 `NameError: name 'err' is not defined`，原始错误被盖住。

**根因**：`lambda: self._fail(err)` 捕获的是变量名，而 Python 3 在 `except` 块结束时会把 `err` 删除；
`root.after(0, ...)` 是异步调度，等回调真正执行时变量已经没了。

**修复**：把值绑成默认参数，创建 lambda 时就把引用固定住：

```python
self.root.after(0, lambda error=err: self._fail(error))
```

**回归验证**：`ruff check .` 从 6 个问题降到 0；手动构造一次失败扫描，界面正常显示失败原因。

**经验**：linter 能发现"这个名字此刻不存在"，但"闭包捕获了会失效的变量"这种时序问题，
还得靠熟悉 Python 的 `except` 作用域规则——工具和语言知识要互补。
